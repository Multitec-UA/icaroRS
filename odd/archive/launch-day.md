# launch-day — Launch-day advisor: manual wind, rail recommendation, L1 checklist

Objective: help the team on the pad: enter the measured wind, get the inclination/heading that lands the rocket closest to the pad, and see the L1 competition limits as a go/no-go checklist, in `packages/icaro`, the API and the web workbench. Needed for the launch on Saturday 2026-11-07 (SURT x SpainRocketry L1, Alcolea de Cinca).
Branch `feat/launch-day` (from `feat/mc-5-explain`). Delivery: single PR into the Monte Carlo chain tracker (#150) or its own PR to main after the chain merges (user decides). Runners: icaro `uv run python -m pytest packages/icaro/tests`; API `cd apps/api && uv run python -m pytest -m "not integration"`; web `cd apps/web && npm test` + `npx tsc --noEmit` + `npm run lint` + `npm run i18n:check` + `npm run api:check`.

- S2 Manual wind. `Scenario.wind: Wind | None` with `speed` (m/s, ≥ 0) and `direction_from` (degrees, 0–360, meteorological: where the wind comes FROM; 270 = from the west, blowing east). When set, `build_environment` keeps the selected atmosphere model's pressure/temperature when it can, otherwise the standard atmosphere, and replaces the wind profile with the constant wind: `wind_u = -speed·sin(direction_from)`, `wind_v = -speed·cos(direction_from)` (u east, v north, RocketPy convention). Implementation: `env.set_atmospheric_model(type="custom_atmosphere", wind_u=..., wind_v=...)` after resolving the base model is acceptable (pressure/temperature then follow the standard atmosphere; document it). Absent → unchanged behaviour. YAML template documents the block.
- S3 Rail recommendation. `recommend_rail(export_dir, scenario, inclinations=(90, 88, 86, 84, 82, 80), headings=range(0, 360, 30)) -> RailSweep`. Runs one deterministic flight per (inclination, heading) with the scenario's atmosphere (and manual wind when given), rail length from the scenario or the export. Each `RailCandidate`: `inclination`, `heading`, `apogee_agl` (m), `landing_distance` (m from the pad), `landing_bearing` (° from north, direction of the landing point), `out_of_rail_velocity` (m/s), `stability_margin_min` (min of `flight.stability_margin(t)` sampled over the ascent up to apogee, calibres), `impact_velocity` (m/s, positive), `checks_ok` (every hard L1 check passes). `best` = the candidate with the smallest `landing_distance` among those with `checks_ok`, else the smallest overall with `checks_ok=False`. `current` = the scenario's own rail setting (or the export's) evaluated the same way. The sweep reuses `build_nominal_flight`; a candidate whose flight raises is skipped and reported in `skipped`. Also returns `wind` as used: `{speed, direction_from, source: "manual"|"model"}` (for `model`, read the environment's wind at pad height + 10 m).
- S4 L1 checklist. `LaunchLimits` dataclass with defaults from the SURT x SpainRocketry L1 guide (Nov 2026, rev. 5): `apogee_max_m=1000` (hard, PROP-003), `apogee_recommended_max_m=600` (soft), `tilt_max_deg=20` (hard, PROP-003: inclination ≥ 70°), `static_margin_min_cal=1.5` (hard, PROP-004, through the whole ascent), `descent_max_ms=10` (hard, REC-003), `descent_recommended_ms=(5, 6)` (soft), `landing_radius_m=500` (soft, REC-003 "se recomienda"), `rail_exit_min_ms=15` (soft, common practice, NOT in the guide — label it so), `wind_max_kmh=32` (hard for going to the rail, Operativa 5.1). `launch_checks(candidate, wind, limits) -> list[LaunchCheck]` with `id`, `value`, `limit`, `comparator` (`<=`, `>=`, `between`), `ok`, `severity` (`hard`|`soft`), `source` (requirement id or "practice"). All values numeric; labels/translations are the surfaces' job.
- S5 API. `POST /api/launchday` body `{export_id, scenario (same shape as /simulate, with optional wind), inclinations?: number[], headings?: number[]}` → 200 `{wind: {speed, direction_from, source}, current: Candidate, best: Candidate | null, candidates: Candidate[] (sorted by landing_distance), skipped: [{inclination, heading, error}], checks_current: Check[], checks_best: Check[] | null, limits: LaunchLimits}` where `Candidate` = S3 fields and `Check` = S4 fields. Synchronous (72 flights ≈ 1–2 min locally; under the 300 s Cloud Run timeout); grid bounded to ≤ 100 candidates (422 otherwise); org-scoped like `/simulate`; does not take the simulate lock (no matplotlib). `inclinations` must be within `[90 - tilt_max, 90]`.
- S6 Web. (a) Time & weather section gets a "Wind on the pad" input: speed (km/h, converted to m/s for the API) + direction-from (°), with a switch "Use the forecast / Enter the wind measured on the pad"; it travels in the scenario body for `/simulate`, `/montecarlo` and `/launchday`. (b) A "Launch day" card in the results column: button "Recommend rail setting" → calls `/launchday` with the current export + scenario, shows a progress state (1–2 min), then: the best candidate ("Inclination 86°, heading 240°: lands ~120 m to the SW"), a table of the top candidates (inclination, heading, landing distance, apogee, rail exit, min stability, checks), an "Apply to rail" button that sets the rail inclination/heading inputs, and the **L1 checklist** for the current setting and for the best one: each check with value, limit, hard/soft and green/amber/red (amber = soft fail), with the requirement id. (c) Everything through i18n (en + es). The deterministic Run and the Monte Carlo stay untouched.
- S7 Tests: domain unit tests with rocketpy mocked (wind vector math incl. the 4 cardinal directions, sweep ordering and `best` selection, skipped candidates, checks for pass/fail/soft, limits defaults); one integration-marked real sweep on the committed export with a small grid; API router tests (422 grid bounds, 404 other org, response shape, no lock taken); web tests for the wind input in the scenario body, the card states, apply-to-rail, checklist colours.
